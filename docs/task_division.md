# TanU_HuBei 五人团队任务分工计划

本文档用于明确 TanU_HuBei 首期开发中五位成员分别负责什么、需要交付什么、如何相互配合，以及每个阶段达到什么条件后才能继续推进。

首期共同目标是：

> 参考 TanU 的模型思想，基于湖北 2030 数据，先完成能够验证的单场景生产模拟主链路，再通过滚动计算扩展到全年 8760 小时。

首期主链路为：

```text
湖北2030原始数据
    -> 统一读取、单位转换和校验
    -> Grid、资源、场景等规范对象
    -> UC/ED生产模拟优化模型
    -> 短周期求解与滚动年度运行
    -> 结果输出、指标计算和物理校验
```

## 1. 分工原则

### 1.1 主责不等于独占

每位成员对一个主要方向负责，包括：

- 拆解该方向的具体任务；
- 维护相关模块的接口和文档；
- 编写主要实现与测试；
- 对该方向的正确性作出解释；
- 处理其他模块接入时发现的问题。

其他成员仍可参与修改，但涉及公共接口或跨模块行为时，应先与主责成员讨论，并通过 Pull Request 审核。

### 1.2 优先打通闭环，再增加复杂功能

开发顺序必须遵循：

```text
脱敏小算例 -> 湖北24小时 -> 湖北168小时 -> 滚动全年8760小时
```

在短周期结果未通过校验前，不直接追求全年求解，也不提前加入完整多场景、市场出清或复杂潮流功能。

### 1.3 统一接口，减少相互等待

五位成员开始大量编码前，必须先确认以下公共接口：

```python
load_case(case_config, time_config) -> CaseData
validate_case_data(case_data) -> DataValidationReport
build_grid(case_data) -> Grid
build_production_model(grid, timeline, formulation_config) -> OptimizationModel
run_production_sim(case_config, run_config) -> SimulationResult
validate_result(grid, result) -> PhysicalCheckReport
```

具体类名以后可以通过 PR 调整，但数据流和模块职责不得随意改变。

## 3. 公共接口与数据约定

本节是所有成员都必须遵守的集成契约。公共接口发生变化时，必须通过单独 PR 修改，并通知受影响成员。

### 3.1 配置接口

配置按用途拆分，禁止重新创建一个包含全部字段的“大配置”。

| 配置 | 目标文件 | 主要内容 | 主责 |
| --- | --- | --- | --- |
| 算例配置 | `configs/cases/hubei2030.yaml` | 数据根目录、文件映射、原始单位、字段映射 | 成员一 |
| 运行配置 | `configs/runs/production_base.yaml` | 时间范围、求解器、建模开关、输出设置 | 成员五 |
| 配置类型 | `src/data/config.py` 或团队确认的位置 | `DataConfig`、`TimeConfig`、`FormulationConfig`、`SolverConfig`、`OutputConfig` | 成员一、成员五 |

配置文件中只能使用相对路径，不得出现任何成员电脑上的绝对路径。

### 3.2 数据层输出接口

成员一读取 Excel 后，应输出规范化的 `CaseData`，而不是把原始 DataFrame 直接传遍整个项目。

`CaseData` 至少应包含：

- 分区和断面数据；
- 火电、水电、储能、抽蓄、风电、光伏和负荷数据；
- 流域及水电机组关联；
- 风、光、负荷和外来电时序；
- 明确的时间索引；
- 原始单位转换后的统一单位；
- 数据来源和校验信息。

成员二只依赖 `CaseData` 构建对象，不直接读取 Excel。

### 3.3 对象层接口

成员二提供的对象应满足：

- 每个资源具有唯一 `id`；
- 每个资源能够关联所属 `zone_id`；
- 水电资源能够关联 `basin_id`；
- 所有物理量字段名称带明确含义和单位；
- 对象层不读取文件、不创建优化变量、不调用求解器。

推荐统一对象包括：

```text
Grid
Zone
Transmission
ThermalUnit
HydroUnit
StorageUnit
RenewableUnit
Load
Basin
Scenario
ScenarioSet
```

### 3.4 优化层接口

成员三、成员四编写的约束函数：

- 只接收规范对象、时间索引和建模配置；
- 不读取 Excel；
- 不负责保存结果；
- 不依赖个人脚本中的全局变量；
- 每类约束放入独立模块；
- 每个核心公式必须具有测试或手算案例。

### 3.5 结果接口

成员五定义统一 `SimulationResult`，至少包含：

- 时间索引和场景标识；
- 各资源逐时出力；
- 火电启停状态；
- 储能充电、放电和 SOC；
- 风光可用出力、实际出力和弃电；
- 分区负荷、发电和交换功率；
- 断面功率；
- 目标函数值和求解状态。

成员五提供的验证模块使用 `Grid + SimulationResult`，不得通过重新读取原始 Excel 判断模型是否满足约束。

## 4. 成员一：湖北数据、配置与数据校验

### 4.1 角色目标

负责把湖北 2030 原始资料转换成其他模块可以稳定使用的规范数据。成员一交付的数据质量会直接决定后续对象构建和优化模型是否可靠。

### 4.2 主要负责目录

```text
configs/cases/
src/data/
docs/data_dictionary.md
tests/data/
```

### 4.3 具体任务

#### A. 建立湖北数据字典

逐类梳理资料中的：

- 文件名和工作表；
- 每一列的含义；
- 原始单位；
- 缺失值和异常值；
- 时间范围和时间粒度；
- 资源 ID、分区、流域和断面的关联关系；
- 同类文件中不同版本之间的差异。

至少覆盖：

- `分区.xls`、`断面.xls`；
- 火电、水电、储能、抽蓄、风电、光伏、负荷文件；
- `流域对应水电.xlsx` 和 `流域三段式/`；
- `电力流/`；
- 各分区风光负荷时序；
- `多场景数据/` 和 `scenario_load_res_18yr_8760.xlsx`。

#### B. 完成算例配置

填写 `configs/cases/hubei2030.yaml`，包括：

- 数据根目录；
- 各类资源文件映射；
- 各类时序文件映射；
- 字段名映射；
- 原始单位声明；
- 日期、时区和时间粒度；
- 可选文件和必需文件的区分。

#### C. 实现统一加载器

实现 `src/data/loader.py`，统一加载不同类别数据。

加载器应支持：

- `.xls` 和 `.xlsx`；
- 单个资源表；
- 8760 小时时序；
- 分区时序；
- 流域三段式数据；
- 外来电时序；
- 可选择的起止时间切片。

禁止为每位成员或每个地区分别复制 `readgriddata_xxx.py`。

#### D. 实现数据校验

实现 `src/data/validators.py`，至少检查：

- 必需文件是否存在；
- 表头和字段是否完整；
- ID 是否缺失或重复；
- 分区、流域和资源关联是否有效；
- 时间索引是否连续；
- 小时数据长度是否符合预期；
- 容量、效率、概率和上下限是否合理；
- 同一物理量的单位是否一致。

### 4.4 交付物

- `docs/data_dictionary.md`；
- 填写完成的 `configs/cases/hubei2030.yaml`；
- 统一数据加载器；
- 数据校验模块；
- `CaseData` 数据结构或与成员二确认的等效接口；
- 数据加载和校验测试；
- 一份不包含敏感数据的结构化加载摘要示例。

### 4.5 验收标准

- 使用一条统一入口能够加载湖北短时间范围数据；
- 能输出资源数量、分区、时间范围和缺失情况摘要；
- 对缺文件、重复 ID、时间缺口和非法效率能够明确报错；
- 其他成员无需了解 Excel 细节即可使用 `CaseData`；
- 原始资料没有被提交到 GitHub。

### 4.6 建议功能分支

```text
feature/hubei-data-dictionary
feature/hubei-case-config
feature/hubei-data-loader
feature/data-validation
```

## 6. 成员三：火电机组组合与系统核心约束

### 6.1 角色目标

负责构建生产模拟中最核心的火电机组组合、系统平衡、断面约束和成本目标，形成可求解的 UC/ED 基础模型。

### 6.2 主要负责目录

- 开机状态；
- 启动状态；
- 停机状态；
- 必要的辅助变量。

#### B. 火电约束

- 出力上下限；
- 开机状态与出力关系；

- 最小停机时间；

- 断面上下限；
- 首期需要的基础备用约束。

### 6.4 交付物

- 火电变量与约束模块；
- 功率平衡与断面约束；
- 成本最小化目标；
- 每类核心约束对应的手算测试；

### 6.5 验收标准

- 多机组小系统功率平衡测试通过；
- 开停机、最小开停机和爬坡边界测试通过；

## 7. 成员四：水电、储能、新能源与场景约束

### 7.1 角色目标

负责火电之外的主要资源建模，使湖北系统中的水电、储能、抽蓄、风电和光伏能够正确参与生产模拟。

### 7.2 主要负责目录

```text
src/optim/constraints/hydro.py
src/optim/constraints/storage.py
src/optim/constraints/renewable.py
src/scenario/
tests/optim/
tests/scenario/
```

### 7.3 具体任务

#### A. 水电与流域约束

实现并测试：

- 水电出力上下限；
- 水电机组与流域关联；
- 流域强迫、预想和平均过程的使用方式；
- 流域或月度能量平衡；
- 缺失或冲突流域数据的处理。

如果资料不足以确认某个约束，应在文档中列为待确认，不自行假设硬规则。

#### B. 储能与抽蓄约束

实现并测试：

- 充电和放电功率；
- SOC 或能量状态更新；
- 充放电效率；
- 能量上下限；
- 初始和末端能量状态；
- 是否禁止同时充放电的建模方式；
- 抽蓄与常规储能差异。

#### C. 风电与光伏约束

实现并测试：

- 可用出力；
- 实际出力上限；
- 弃风、弃光；
- 装机容量与标幺时序的换算；
- 不同分区新能源时序关联。

#### D. 场景处理

首期只需支持：

- 单场景规范接口；

- 能从单场景平滑扩展到多场景，而不在约束中硬编码场景名称。

复杂聚类和场景削减放入后续路线图。

### 7.4 交付物

- 水电和流域约束；
- 储能与抽蓄约束；
- 风电和光伏约束；
- 单场景基础接口；
- 各资源手算测试和边界测试；

- 储能 SOC 手算案例逐时一致；
- 储能能量和功率不越界；
- 风光实际出力不超过可用出力；
- 弃风弃光量计算正确；
- 水电和流域关联正确，能量约束可解释；

## 8. 成员五：应用集成、年度运行、输出与验证

### 8.1 角色目标

负责把其他成员交付的模块组织成可运行的生产模拟应用，并建立结果结构、物理校验、滚动年度运行和团队集成测试。

成员五不是替其他成员修补所有代码，而是负责尽早发现接口问题，并推动问题回到对应主责模块解决。

### 8.2 主要负责目录

```text
configs/runs/
src/simulation/
src/output/
src/metrics/
src/validation/
src/visualization/
runcase/
tests/integration/
```

### 8.3 具体任务

#### A. 定义运行配置

填写 `configs/runs/production_base.yaml`，包括：

- 时间范围；
- 时间粒度；
- UC 或 ED 建模模式；
- 求解器名称和参数；
- 是否启用备用等建模开关；
- 输出目录和输出内容；
- 滚动窗口长度和重叠时段。

#### B. 构建生产模拟应用

实现：

```python
run_production_sim(case_config, run_config) -> SimulationResult
```

应用流程应包括：

1. 加载配置；
2. 调用成员一的数据加载器；
3. 调用成员二的 Grid 构建器；
4. 调用成员三和成员四的约束与目标函数；
5. 调用求解器；
6. 提取结果；
7. 调用验证和输出模块。

#### C. 实现运行入口

实现 `runcase/run_hubei_annual.py`。

运行入口只负责：

- 解析参数；
- 指定算例配置和运行配置；
- 调用生产模拟应用；
- 输出运行状态。

不得在入口脚本中直接写优化约束。

#### D. 短周期与滚动年度运行

按顺序打通：

1. 脱敏小算例；
2. 湖北 24 小时；
3. 湖北 168 小时；
4. 滚动窗口状态传递；
5. 全年 8760 小时结果拼接。

滚动状态至少包括：

- 火电启停状态和持续开停时间；
- 储能期末 SOC；
- 需要跨窗口传递的其他状态。

#### E. 结果输出与指标

定义 `SimulationResult`，实现：

- 原始逐时结果写入；
- 汇总指标；
- 求解状态和运行日志；
- 结果目录组织；
- 最小必要可视化。

#### F. 物理校验与集成测试

实现自动检查：

- 分区功率平衡；
- 机组出力上下限；
- 火电爬坡和启停状态；
- 储能 SOC 和能量更新；
- 新能源可用出力和弃电；
- 断面越限；
- 窗口之间状态连续性。

### 8.4 交付物

- 运行配置；
- 生产模拟应用；
- 湖北年度运行入口；
- `SimulationResult`；
- 输出、指标和验证模块；
- 24 小时、168 小时和滚动年度集成测试；
- 运行与问题记录文档。

### 8.5 验收标准

- 能通过统一入口运行脱敏小算例；
- 能完成湖北 24 小时端到端运行；
- 能完成湖北 168 小时运行并输出校验报告；
- 能通过滚动窗口拼接全年结果，或明确记录阻塞原因；
- 输出结果字段、单位和时间索引完整；
- 物理校验能够发现故意制造的错误结果。

## 9. 成员之间的协作与互审关系

为了避免模块完成后才发现接口无法连接，每个主责模块都设置固定互审关系。

| 提交内容 | 主责成员 | 必须参与审核的成员 | 审核重点 |
| --- | --- | --- | --- |
| 数据字典、配置、加载器 | 成员一 | 成员二、成员五 | 输出是否足够构建对象和运行应用 |
| 对象与 Grid 构建器 | 成员二 | 成员一、成员三、成员四 | 数据映射、字段单位、约束使用是否方便 |
| 火电、平衡、断面和目标 | 成员三 | 成员四、成员五 | 公式正确性、与其他资源接口、结果提取 |
| 水电、储能、新能源和场景 | 成员四 | 成员三、成员五 | 公式正确性、是否能接入平衡和目标 |
| 应用、输出、验证与年度运行 | 成员五 | 全体成员 | 集成流程、结果含义、校验覆盖 |

跨模块问题处理原则：

1. 先确认问题属于数据、对象、约束还是应用层；
2. 在对应 Issue 中记录复现方式；
3. 由主责成员修复其模块；
4. 发现问题的成员补充集成测试；
5. 不在应用层临时绕过底层错误。

## 11. 每位成员的完成定义

一个任务不能仅以“代码写完”作为完成标准。每位成员的任务同时满足以下条件才算完成：

- 代码位于正确模块，没有越过职责边界；
- 公共接口与团队约定一致；
- 有正常情况和异常情况测试；
- 有使用说明或接口说明；
- 通过至少一位指定成员审核；
- 已合并到 `dev`；
- 能被成员五的集成流程调用；
- 不包含原始数据、个人路径或无关文件；
- 主责成员能够解释实现逻辑和物理含义。

## 12. GitHub 执行方式

### 12.1 Issue

每个可独立验收的任务建立一个 Issue。Issue 应包含：

- 任务背景；
- 输入和输出；
- 计划修改的模块；
- 验收条件；
- 依赖的其他 Issue；
- 待确认问题。

### 12.2 分支

每个任务从最新 `dev` 创建短期分支：

```bash
git switch dev
git pull origin dev
git switch -c feature/<task-name>
```

不要为每位成员创建一个长期个人分支，也不要在一个分支中同时完成多个无关任务。

### 12.3 Pull Request

所有功能通过 PR 合并到 `dev`。PR 应说明：

- 完成了哪个 Issue；
- 修改了什么；
- 公共接口是否变化；
- 如何测试；
- 测试结果；
- 尚未解决的问题；
- 指定审核成员。

### 12.4 每次集成前检查

```bash
git status
pytest
```

提交前还应确认：

- 没有提交 `datasets/hubei2030/`；
- 没有提交 `results/` 大文件；
- 没有提交 `.idea/`；
- 没有写入个人绝对路径；
- 没有把多个无关任务放入同一 PR。
